## 二、变更内容描述

### 2.1 现状

项目当前处于 V2 AI Agent 设计基线已立（D-013，2026-08-01）、但**未开始任何代码实施**的状态：

- D-013（`docs/08-pending-decisions.md`）已决定：引入 PgVector 向量库 + langchain4j 作 `AiProviderClient` 端口实现层 + Agent 受限工具调用 + 激活社区助手与内容审核。
- `docs/09-ai-agent-design.md`（CI-DOC-018）已建立设计基线，含 PgVector schema、8 条安全边界（B1-B8）、M8.0-M8.5 切片规划。
- `pom.xml` 无 langchain4j/onnx/djl 依赖（grep 零命中）；`docker-compose.yml` 只有 mysql 无 postgres；`schema.sql` 无 `ai_tool_call_log`/`ai_chat_memory` 表；`admin_permission` 无 V2 RBAC 权限码（7055-7056）。
- `.env.example` / `application*.yml` 仅有 V1 `AI_PROVIDER_ENABLED`/`DEEPSEEK_*`，无 V2 的 `AI_AGENT_ENABLED`/`PGVECTOR_*`/`AI_EMBEDDING_*` 等键。
- 现状带来的问题：M8.0（基建切片）无法启动——①无 PgVector 容器，向量检索无运行环境；②配置键缺失，`@ConditionalOnProperty` 无法生效；③schema 未同步，新表无处落地；④测试 profile 缺失，无法验证；⑤设计文档有 7 处内部矛盾（C-1~C-7）会导致实施期返工。

此外，文档 agent 与环境 agent 联合检查确认：09 文档存在 7 处内部矛盾（`ai_tool_call_log` 归属库不明、RBAC 权限码无 ID 且 MODERATOR 角色不存在、vector 维度硬编码与可配冲突、ChatMemoryStore 适配方式不明、H5 SSE 鉴权方案缺失、ONNX 模型分发未落地、登记表与实物不一致）。

### 2.2 期望

本 CR 是 M8.0 切片的"**第 0 步**"——把开发与运行的脚手架立起来，让后续 langchain4j 业务代码切片能在干净基线上开跑。**本 CR 不写业务代码**（langchain4j 接入、Agent/Tool/RAG 的 Java 实现留给 M8.0 切片单独评审）：

1. **PgVector 运行环境**：`docker-compose.yml` 新增 `postgres` 服务（`pgvector/pgvector:pg16`，agent 已验证 0.8.6 可用）+ 持久卷；新建 `schema-pgvector.sql`（CI-DB-017）含 `CREATE EXTENSION vector` + `ai_knowledge_doc`/`ai_embedding` 表 + HNSW 索引。
2. **配置键就位**：`.env.example` + `application.yml`/`application-dev.yml`/`application-prod.yml`/`application-test.yml` 加 V2 配置段（`AI_AGENT_ENABLED`/`AI_RAG_ENABLED`/`PGVECTOR_*`/`AI_EMBEDDING_*`/限流/审核/知识库重建），全部默认关闭、走环境变量。
3. **MySQL 侧 schema 同步**：新增 3 张表（`ai_tool_call_log` CI-DB-019 / `ai_chat_memory` CI-DB-020）+ V2 RBAC（MODERATOR 角色 + 7055-7056 权限码，CI-DB-018）；同步 `schema.sql`/`schema-h2.sql`/`schema-mysql-test.sql`/`data-dev.sql` 四处保持 PCA 一致。
4. **测试脚手架**：pom 加 `tc-pgvector` profile（克隆 tc-mysql 范式）+ testcontainers-postgresql 依赖 + `AbstractTcPgVectorIT` 基类 + `application-tc-pgvector.yml`。
5. **模型分发方案**：`.gitignore` 排除 `*.onnx`；`models/README.md` 记录 embedding/nsfw 模型来源与 sha256 校验方式。
6. **09 文档矛盾修正**：C-1~C-6 共 6 处内部矛盾修订（C-7 随本 CR 登记表同步消除）。
7. **pom 版本管理**：`<properties>` 声明 langchain4j/onnxruntime/djl 版本号（本轮**不加 dependency**，留 M8.0 切片引入业务依赖时单独评审架构守卫影响）。

### 2.3 变更理由

- **业务诉求**：D-013 已立设计基线，需打通"设计→实施"的最后一段路——运行环境、配置、schema、测试脚手架缺一不可。
- **风险驱动**：09 文档 7 处内部矛盾若不在实施前修正，M8.0 编码期会反复返工（如 RBAC 权限码冲突、ChatMemoryStore 适配方式不明）。本 CR 一次性消除矛盾。
- **合规边界**：本 CR 严格遵守 D-013 八条安全边界（B1-B8）——不引入 langchain4j 业务依赖（留 M8.0 单独评审 `AiProviderArchitectureTest` 影响）、不解除 `AiPostAssistantController` 401（留 M8.3）、不改架构守卫测试（留 M8.0 加 `LangChain4jProviderClient` 时同步改）。
- **配置管理**：本 CR 属 C 类重大变更（新增数据库 schema + 改受控 CI-BS-011/CI-RC-001/CI-BS-001），按 CMP §6 必须走变更控制，建立 CR 留审计证据。
